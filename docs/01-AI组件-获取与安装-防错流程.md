# AI 组件：取得载荷、真正登记产品、独立验证

适用范围：本研究固定的 Windows 11 x64 版本和内部部署 ABI。没有验证 Windows 11 22H2 起所有版本，也没有“照做必成功”的保证。先读 [重建资产](06-源码与资产重建.md)，克隆仓库不等于已取得安装包。

## 先分清三层

1. **包**：MSIX 被 staged、注册给用户或 provisioning，分别是不同状态。
2. **产品**：RUM 描述产品、实体、载荷和版本；安装插件建立 UUP 产品与包的关系。
3. **执行**：工作负载管理器选中产品，模型宿主成功加载模型和执行后端，实际完成推理。

本次标准 AppX 安装没有补齐所需产品关系；原版 UALite 产品部署链可以做到。不能据此断言产品关系“只有在线 Windows Update 能写入”。我们已经用离线内容目录走原版部署插件登记成功，无需手写数据库。

## 1. 从哪里取原版内容

本研究从微软 LCU 的 MSU/WIM 内提取 AI MSIX、`onepackage.AggregatedMetadata.cab`、产品 RUM CAB 和部署引擎。部分 MSU 的资源未压缩，因此可以先解析索引，再按 HTTP Range 下载指定资源；不是任意 MSU 都能这样处理。

已用 UUP dump 索引标识：

| 样本 | 索引标识 |
|---|---|
| KB5124010 / 26300.9550 | `fe47c57f-a77f-41e3-9012-00b4187e3462` |
| KB5066835 / 旧代样本 | `15127f8d-75c8-4150-98d1-5020aa815a35` |

UUP dump 提供索引，实际二进制取自微软 CDN。标识和 URL 可失效，需检查接口结果和实际文件名。取得文件的流程及脚本见 [重建资产](06-源码与资产重建.md)。

RUM 原文保存在 `evidence/rum-definitions/`，用于审阅和还原清单；安装仍使用从原始更新取得的 RUM CAB，不能随意重打包 JSON 冒充原版元数据。

## 2. 准备一个产品的内容目录

```text
产品内容目录/
  metadata/
    ualite.dll、原版插件 DLL 和 JSON 配置
    一个匹配的 Windows.Workload.*.rum.json.cab
  <RUM 声明的 PayloadName>.msix
  ...其余精确版本载荷...
```

- 当前已验证引擎从内容目录根层查找载荷；仅放在 `load/` 不够。
- 文件名、架构、Identity 版本须按 **实际 RUM** 匹配。旧样本有 GUID 文件名，新样本有包名文件名；不要只凭代际猜。
- 检查下载摘要、完整 MSIX 的签名和 AppxManifest Identity。版本不同不能靠改名解决。
- `evidence/installer-engine-files.json` 保存本次引擎身份；窄化权限的插件 SHA256 是 `953bae4080a784fc93b3aba38153c4bb78689c874a1660e99928b99a06d0abef`。

## 3. 调用原版部署会话

`native-install/tools/run_install.py` 已移除对 Codex 内置 PowerShell 的依赖，使用 PATH 的 PowerShell 7、`UNLOCK_COPILOT_PWSH` 或 `--pwsh` 参数。它默认只做原生规划，实际部署必须指定 `--install`。历史下载脚本仍有旧目录，现行重建优先使用 06 的入口。

在管理员 PowerShell 中，一次只装一个产品。例如：

```powershell
$repo = (Get-Location).Path   # 当前目录应为仓库根目录
$py = (Get-Command python.exe).Source
$product = 'Windows.Workload.ContentExtraction.LNL.amd64'
$content = Join-Path $repo "ai-products\$product"
$run = 'attempt-review-new1'  # 使用未出现过的新名字
& $py -u "$repo\native-install\tools\run_install.py" `
  $run $content "$product.rum.json.cab" $product --install
```

此命令会实际安装，不用于已有机器的单纯核验。先备份产品清单、相关注册表和自己的改动记录。不要为了让示例跑起来而删除已有 IFEO 或改变整棵注册表 ACL。

先用同一命令的 `--validate-only` 做普通文件核对，再在管理员进程使用 `--plan-only` 运行原版规划。前者不运行 Frida/部署 DLL，后者不调用 Install。RUM 的 ProductIdentifier 本身不带 `.amd64`，需与 ProductArchitecture 组合为本工具的完整产品 ID；文件命名和 CLI 用完整 ID。

内部顺序已在固定版本动态验证：

```text
管理员进程 / MTA 初始化
→ 设置可写 UALITE_GLOBAL_LOG_FILE_PATH
→ CreateDeploymentSessionEx(1, 内容目录, &GUID_NULL, 2, &56字节选项, &session)
→ 选项区首指针指向 {"ModuleID":"LocalServicingOnline"} 的 UTF-16 字符串
→ 原始 session +0x20: GenerateDownloadRequest
→ request +0x28: GetFileRequests → collection +0x18: Count
→ 本工具要求 Count == 0，才调用原始 session +0x28: Install
```

这是私有 ABI，不是公开 SDK；不同对象相同偏移不是同一个方法。当前工具只处理“所有文件已在本地”的模式，Count>0 时停止并不证明 Windows 自身不能下载。

安装进程中的 Hook 只把插件返回地址 RVA `0x996e6` 对 `HKLM\SOFTWARE` 的 `RegOpenKeyExW` 请求从 `KEY_ALL_ACCESS(0xf003f)` 改为 `KEY_READ(0x20019)`，仍由 Windows 返回真实句柄，不伪造成功，也不修改 ACL。不同 DLL 版本不能直接复用该地址。

## 4. 判断是否成功

分别检查以下证据，不把其中一项当作全部结果：

1. `*.events.txt`：`fileRequestCount count=0`、`install.begin`、`install.end` 及真实 HRESULT。
2. 原生日志：实际 Stage、安装插件运行、`SRAddOrUpdateUupProduct` 等记录。
3. `Get-AppxPackage -AllUsers`：Identity、版本、Status，以及用户注册还是机器 Staged。
4. StateRepository：对应产品行和包关系，核对包名/版本/Flags，而非只看行数。
5. `native-install/tools/enumerate_components.py`：在安装进程退出后的普通新进程中枚举组件。
6. 最后再单独测试 GetReadyState、模型创建、真实输入推理和对应界面。

数据库核验优先使用新收录的 `tools/inspect-uup-products.py`：对已有可读数据库使用 SQLite 只读事务，可另用 SQLite backup API 生成一致快照。权限不足时报告权限问题，不能把错误当成产品不存在。

WAL 模式下，只拷贝 `.srd` 主文件可能读到旧数据；但依次复制 `.srd`、`-wal`、`-shm` **也不自动保证运行中数据库的一致性**。应使用事务/备份 API 或可靠的一致快照。`-shm` 是共享内存索引，可以重建，不能写成“任何时候三文件缺一不可”。不使用 `immutable=1` 忽略活跃 WAL，不把快照写回系统库。

## 5. 常见失败如何判断

| 现象 | 先查什么 |
|---|---|
| Count>0 | 载荷根目录、PayloadName、版本、架构、内容完整性 |
| `0x8024200D` | 这是 WU_E_UH_NEEDANOTHERDOWNLOAD，不能当成功；核对真实请求和日志 |
| Install 返回 0，产品仍不见 | 先排除旧快照、查重名行和安装器是否真正执行，不能立即归咎于已装包 |
| `0xc1570106` | 既有实验与并发相关；串行并查日志，不把错误码当唯一根因 |
| `0x80073D3B` | 已有产品请求在本机不适用/无法解析的结果；单凭此码不能判断本次有没有访问网络 |
| `0x80040154` | 类未注册，需查激活对象、包身份和服务；不是 NPU 专用错误 |
| `0x80004001` | E_NOTIMPL，查具体接口和所选后端，不能直接等同“需要 NPU” |

过去有一轮通过卸载后重新 staging 触发了登记。这是**针对特定状态的恢复实验**，不是每次安装的前置条件。不要循环卸载 RUM 的全部载荷：Manager、SessionManager、WinMLShared 等可能被多个产品共享。若确需重装，先确定共享关系和可恢复载荷，仅处理已经定位的目标。

## 不应再沿用的说法

“微软只有 11 个 AI 产品”“没有通用包所以请求必失败”“365 就等于所有推理只在云端”“STX 是 Intel 平台”都不是本次证据能支持的通用结论。11 仅是一个已提取样本中的集合，STX 与 AMD Strix 路线相关；不适合本机不等于没发布。HybridCompute 是组件/执行路径名称，其具体是否本地或远程需另外验证。
