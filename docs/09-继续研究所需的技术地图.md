# 没有聊天记录时，从这里继续

目的：区分各条链路的职责、已经推翻的假设和可直接开始的下一步。具体地址/摘要在 04 和源码；系统变版时先重新核对。

## 1. 组件各负责哪一层

| 层 | 组件/资产 | 应当问的问题 |
|---|---|---|
| 应用能力判定 | Windows AI API / 应用使用的 Windows App SDK | 为什么 GetReadyState 不可用？是否在此进程提前被 UI 拦住？ |
| 选产品/工作负载 | WorkloadManager、Microsoft.Windows.Workloads.dll、WSAIFabricHost.dll | 本次选的是通用、365 还是 LNL？版本和依赖能否解析？ |
| 部署 | RUM、UALite、MsixDeployment 插件、AppX/StateRepository | 真正 Stage 了哪些包，是否登记产品与包关系？ |
| 执行宿主 | 原版 WorkloadsSessionHost.exe、Manager/SessionManager 包 | WinRT 激活和工厂注册是否成功？启动保护是否阻止 Hook？ |
| 具体模型/后端 | cacheapi、srdapi、OCR 会话、OpenVINO | 选择 CPU 还是 NPU，输入输出和真实结果是什么？ |
| Shell | ClickToDo.exe、DiscoveryOverlay、Explorer | 入口、窗口激活、选择和动作分发在哪一步退出？ |

WorkloadManager 是 Windows AI 工作负载的软件接口/实现链，不是每个应用各写一套，也不是一个叫 WorkloadManager 的物理芯片。应用实际加载的 SDK/DLL 可能不同；Gallery 不受某份系统 JSON/DLL 改动影响，不能据此推定它完全不走系统服务。

HybridCompute 也是软件组件/接口路径。缺失相应类或实现并不等于“没有一块 HybridCompute 硬件”，也不能由名称就断言它只运行在云端。此前 365 路线未取得完整可用实现，因此实际工作转向 LNL。

## 2. 关键转折，避免重走弯路

- 最早只是 AppX 安装包，产品关系缺失。后来已通过**原版离线部署插件**写入关系；不再需要直接写 StateRepository。
- 服务器请求失败与本地不适用不能只凭 `0x80073D3B` 判断。没有捕获到在线请求不等于服务器上产品不存在。
- 11 个 RUM 仅代表一个更新样本；通用产品、其他 AI 产品和 Phi Silica 的可取得性仍是有范围的未知，不能全称否定。
- LNL 产品中的各模型不是一条执行路径：OCR 可走 CPU，不代表场景检测自动回退。CTD 的 cacheapi/srdapi 另有 NPU 选择，已在真实宿主内改为 CPU。
- 只把 GetReadyState 改成 Ready，不会补齐包、产品、宿主工厂和模型后端。系统所有应用统一 Ready 尚未解决。
- 客户端曾在推理成功后崩溃；去掉 RaiseException/RtlRaiseException 观察 Hook 后稳定。不要把调试 Hook 全部叠加到成功版本。
- 复制/打开曾无反应，用户重启后确认可用。没有定位到专门修复，不得编造原因。

WinRT ABI 不明时不要猜槽：旧异步状态探针曾读错接口，后来通过 QueryInterface(IAsyncInfo) 校正。发布的私有接口探针仍绑定本次二进制；HRESULT、bool、HSTRING 和 COM 指针不能混读。接口列表可查仓库 `winmd-iids/`；历史探针也可能有错误，先核对当前 winmd/反编译。

## 3. Click to Do 下一步只攻 Win＋单击

已知：同一个已预热客户端，原生 Win＋Q 可以选择内容；Win＋单击会短暂显示后消失。手势经过 dispatch `0x1c13c4` / activation `0x1bcc00`，没有记录相同 URI 路径。事件查询未证明进程崩溃。

下一轮应：

1. 使用已验证启动器，确认客户端 PID/文件摘要和模型 Hook 就绪。
2. 对成功 Win＋Q 与真实 Win＋单击分别记录原生调用入参、对象阶段、窗口显示/激活/失焦与最早取消点。
3. 把两个时间线对齐，找**第一个**分歧，而非对所有返回值强制成功。
4. 只对已定位的手势分支做一个可撤销实验，用户确认是否保持界面和选择。
5. 验证正常退出，再考虑整合。用户已选择继续 Windows 原生入口，暂不接管全局快捷键。

Explorer 的原生 Win＋Q 协调在 `work/phase26-shell-entry/`，客户端 Hook 在 phase19/23，宿主在 phase21。phase25 是成功脚本的 GUI 封装；构建器的文本替换仍是版本绑定实现，不是通用补丁生成器。

## 4. Studio 的下一步

设备层已由软件主节点＋原版 INF 自动创建子组件解决，不需要模拟物理 NPU。旧并列 ROOT 节点把资源查询指向错误父节点；ParentPresent 单次留存也没能保证重启枚举，后来改为 V2 服务。

模型层保留原版 PerceptionCore/相机外壳，取旧 7D1D 包完整 IR 图，转布局、选择姿态图中间输出、编译 CPU blob、装回新版 EPContext 壳，再改执行插件和内存选择。四个资源 101/109/113/132 可建立 CPU 会话并离线推理；用户确认的 GUI 效果只有自动取景和背景模糊。

资源 119 仍是未适配的 NPU 产物。优先做单开关与模型调用的对应实验，再找输入输出语义接近的完整旧图。不要将名字直接等同到某个 GUI 开关，也不要用常量伪造模型输出。

长期需要：真正整机重启后的效果验收、不同相机/CPU、长时间运行、服务更新与回退。冷目录模型推理通过不补足这些验证。

## 5. 阅读失败记录的正确方式

`evidence/` 是带日期的历史证据，不是可直接导入的运行状态。RUM 原文保存产品定义；实际安装用原始 CAB。`source-copy-manifest.json` 是复制当时的摘要，后续可维护的源码修改以 Git 为准。

最小现场报告应包括：系统/包/文件版本和摘要、入口/进程、已观察的最后成功点、首个失败 HRESULT 或行为、是否实际发出网络请求、可撤销的下一项实验。先报告重大阻塞，再继续长时间分析。
